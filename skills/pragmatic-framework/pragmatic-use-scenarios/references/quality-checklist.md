# Use Scenario Quality Checklist

Use this checklist to evaluate any use scenario before publishing or sharing with the team.

---

## Persona Integrity
- [ ] The scenario focuses on **exactly one** user persona
- [ ] The persona is named and their context is established
- [ ] The persona is drawn from validated User Personas (market-grounded, not invented)
- [ ] The persona's role, environment, and relevant attributes are clear from context

## Problem Clarity
- [ ] The scenario describes **exactly one** problem or friction point
- [ ] The problem is concrete and specific — not abstract or generic
- [ ] The frequency/timing of the problem is indicated (e.g., "every quarter," "at checkout")
- [ ] The stakes are clear — what is the consequence of this problem going unsolved?

## Solution-Free Language (Critical)
- [ ] No product features are named or implied
- [ ] No UI elements or system components are referenced
- [ ] No words like "should," "could," "needs a way to," "wishes the app would"
- [ ] The scenario ends at the problem, not at a proposed fix
- [ ] No current workarounds are presented as solutions

## Narrative Quality
- [ ] Written in third-person narrative form
- [ ] Reads as a story, not a bullet list or process document
- [ ] Contains emotional or business impact (frustration, risk, cost, confusion)
- [ ] Is vivid enough that a developer or designer would feel the user's pain
- [ ] Is not so long that it loses focus (target: 3–8 sentences; complex scenarios may be longer)

## Market Grounding (NIHITO)
- [ ] The scenario reflects real observations from customer/user interviews or research
- [ ] It is not purely hypothetical or assumed by the internal team
- [ ] It would resonate with multiple real users, not just one edge case

## Integration
- [ ] The scenario is linked or traceable to a specific requirement
- [ ] The scenario is linked to its source User Persona document
- [ ] The scenario has a version/date so it can be updated as the market changes

---

## Quick Diagnostic Questions

Ask these to identify problems fast:

1. **"Who is in this scenario?"** — If the answer is vague or includes multiple personas, revise.
2. **"What solution does this imply?"** — If you can answer this, the scenario has solution creep.
3. **"Would a developer know why this matters?"** — If not, add emotional/business stakes.
4. **"Did we hear this from a real user?"** — If not, flag for validation before using.
5. **"Could this apply to a competitor's product too?"** — If yes, that's a good sign (it's describing a market problem, not a product spec).
