# Experiment Plan Template

A one-page plan for testing a concept with real users before committing to full delivery. Write one plan per experiment. Set the success threshold and the decision rule **before** the test runs, so the result can't be argued into whatever the team hoped for.

## When to Use

- After a workshop or Ideation Brief names a riskiest assumption
- Before spending design or engineering time beyond a cheap prototype
- When the team disagrees about whether an idea is good: test it instead of debating it

---

## Experiment Plan

**Concept:** *(name and link to the Ideation Brief)*
**Owner:** *(one person)*
**Dates:** *(start / end; most experiments should take days or a couple of weeks)*

### 1. Market problem
*Which validated market problem does this concept address, for which persona?*

### 2. Hypothesis
*"We believe that [persona] will [behavior] because [reason]. We'll know we're right when [measurable signal]."*

### 3. Riskiest assumption
*The one assumption that, if wrong, kills the concept. Desirability, usability, viability or feasibility?*

### 4. Test method
*The cheapest test that could prove the hypothesis wrong.* Common options:

| Method | Good for testing |
|---|---|
| Problem / concept interviews | Whether the problem and concept resonate |
| Paper or clickable prototype, task-based usability test | Whether users understand and can use it |
| Fake door / landing page / pre-order | Whether people want it enough to act |
| Concierge or Wizard-of-Oz (deliver manually behind the scenes) | Whether the outcome is valuable before automating it |
| Technical spike / proof of concept | Whether it can be built at acceptable cost |
| Limited pilot or A/B test | Whether behavior changes at real scale |

**What we'll build or prepare:** ______________________

### 5. Users
- **Who:** *(persona; recruit real target users, not colleagues or only friendly customers)*
- **How many:** *(e.g., 5-8 for usability, enough traffic for a fake door to be meaningful)*
- **How recruited:** ______________________
- **Who from the team observes:** *(include the people who will build it)*

### 6. Success threshold
*The specific, measurable result that counts as a pass. Decide it now.*

- Metric: ______________________
- Pass if: ______________________ *(e.g., "6 of 8 users complete the reconciliation task in under 5 minutes without help")*
- Fail if: ______________________

### 7. Decision
*Agreed in advance:*

- **If it passes:** ______________________ *(e.g., next experiment on the next-riskiest assumption, or hand to Requirements)*
- **If it fails:** ______________________ *(change the concept and re-test, or drop it)*
- **Decision owner:** ______________________

## Results (complete after the test)

- **What happened:** *(numbers first, then observations)*
- **Met threshold?** Yes / No
- **What surprised us:** ______________________
- **Decision taken:** Keep / Change and re-test / Drop
- **What we learned (even if dropped):** ______________________
- **Update:** Ideation Brief section 6, idea portfolio, and, if kept, the requirements (`pragmatic-requirements`)

---

## Checklist

- [ ] Hypothesis is falsifiable
- [ ] Riskiest assumption, not the easiest one, is being tested
- [ ] Test participants are real target users
- [ ] Success threshold and decision rule were written before the test
- [ ] Builders observed the test, not only the product manager
- [ ] Result and decision were recorded, including for dropped ideas
